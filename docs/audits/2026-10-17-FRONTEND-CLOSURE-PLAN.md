## F-01 — P2: RF-01 пропускает waiting после собственного save

Текущий `use-product-story-editor.ts`, ветка `revisionChanged && confirmed && !snapshotBelongs`: `replace({ ...previous, identity })` сохраняет awaitingOwnerSnapshot=false. Последующие change/save допускаются, несмотря на чужой snapshot. Обычный waiting-путь теперь защищён, исключение собственного save — нет.

**Воспроизведено на 6d0f41c2:** создать paragraph → успешно save → очистить mock вызовов API → render r2 со snapshot, помеченным r1 → edit paragraph → save. `replaceCreation` вызывается один раз; ожидалось ноль. Это hook-level проверка заявленного контракта; экран подаёт identity/snapshot из одного ответа, поэтому реальный браузерный сценарий их рассогласования здесь не доказан.

**Решение:** флаг готовности baseline должен следовать ownership во всех переходах, включая сохранение previous blocks после подтверждённой операции. Старые блоки можно временно показывать, но нельзя редактировать/отправлять под другой revision. Провести узкую таблицу переходов: cold mount; новая работа без snapshot; новая revision/foreign snapshot без и после собственного save; совпадающий snapshot с прежним token; смена account/product. Не добавлять ещё одну эвристику token или общий framework.

**Приёмка:** дополнительная последовательность выше зелёная; edit/upload/save не вызывают effects в waiting; корректный snapshot с равным token разблокирует; ввод до первого сохранения остаётся доступным. Уточнить статус RF-01 после проверки, не ссылаться только на прежние 35/35.

## F-02 — P2: незавершённая правка общего AppDialog требует проверки потребителей

Незакоммиченный diff заменяет web maxHeight='100%' на `Math.max(height - viewportGutter * 2, 0)`. Это допустимое направление: viewport-зависимый предел не является вредным хардкодом. Однако shared owner используется не только recovery.

**Решение:** закончить текущую правку у владельца AppDialog, проверить способ получения height, изменение viewport, внешние gutters и Safe Area (не вычитать их дважды). Не лечить проблему maxHeight внутри product screen. Не добавлять вложенный ScrollView поверх уже существующего.

**Приёмка:** recovery ~8k текста в Chromium/WebKit — последний абзац и закрытие доступны, текст выделяется/копируется, нет горизонтального overflow; Escape/close возвращают фокус. Дополнительно один короткий обычный dialog и один sheet на 390×400 и нормальной высоте, resize при открытом диалоге. Существующие AppDialog owner specs и native contract не ломаются. Выделение любого абзаца допустимо для теста базовой возможности выделения; для полной доступности отдельно проверять последний абзац и нижние действия. `scrollHeight > clientHeight` без реальной прокрутки и видимости цели недостаточно.

**Решение:** существующие `useAppTheme` и SemanticColorMap — единственный активный источник. Цветозависимые styles вычислять в render либо передавать palette чистому helper. - Не объединять заново принятые wrappers/owners; не дробить экран по лимиту строк.
- Не мигрировать SDK/private imports/browser history без подтверждённого блокирующего сценария.
- Не переписывать API/DB/ставки/права в рамках визуальной подготовки.
- `fill('')` оставить в validation-тесте. Отдельно коротко проверить Select All/Delete на обычном input и реальном TextField: если дефект продукта воспроизводится, исправить owner; если нет — не заводить гипотезу как обязательный блокер UI.
- Старые media-lifecycle/search-overlay failures: сверить, относятся ли они к текущему SHA/затронутому flow. Предсуществование не делает пользовательскую потерю данных приемлемой; но исторический красный лог без актуального воспроизведения не повод запускать все suites или переписывать поиск.
- Не превращать каждый local gap/число в токен. Централизуются повторяемые роли, уникальная геометрия остаётся у композиции с provenance.

## Правило остановки технической волны

Можно начинать следующий экран, когда F-01/F-02 закрыты, эталон использует общую theme/component основу, recovery и responsive/zoom приёмка завершены, финальный build проходит, а оставшиеся пункты явно вынесены в screen-by-screen очередь. Нельзя объявлять полностью готовый black/desktop UI до дизайнерского решения. Следующий экран выбирать по пользовательскому приоритету (например, профиль автора), с exact Figma node и теми же проверками. Никакого дополнительного «ещё одного полного аудита всего проекта» по умолчанию.
