### W5-01 — P1: DR-01 закрыт не полностью, подтверждение своего save остаётся эвристикой
Файлы: `apps/mobile/src/features/sellers/use-product-story-editor.ts:202,379–400,640`.
`confirmedSave` хранит только storyToken. После save и обычного refetch той же ревизии флаг остаётся установлен. Следующая произвольная ревизия с token <= сохранённого воспринимается как результат своего сохранения, хотя token сравним только внутри ревизии. Нет проверки конкретной операции/целевой ревизии (нет даже sameProduct в этой ветке).
Воспроизведение: mount r1 → save «Текст» (token1) → refetch r1/token1 → внешняя r2/token0/«External revision». Ожидается External revision, фактически Текст. Дополнительный hook-тест красный на HEAD. Это риск показа/последующего сохранения устаревшего содержимого.
Целевое решение: убрать вывод о принадлежности revision по величине token. Серверный revisionId определяет baseline; координация собственного save/refetch принадлежит владельцу состояния товара. Сохранённый ответ следует применять к конкретному account/product/revision и подтверждённой операции; переход к иной revision должен гидратировать её данные. Для промежуточного несогласованного product-detail/query состояния передавать снимок с его revisionId, не выдавать старую story за новую. Если текущий ответ не содержит target revision, не угадывать её: дождаться согласованного refetch/использовать существующий ответ владельца product query. Не менять серверную модель сохранения и не вводить новый API ради обхода.
Критерии: (1) описанная последовательность зелёная; (2) смена product/account после save не переносит blocks; (3) собственный save с запаздывающим query не откатывает шаги/текст; (4) token никогда не сравнивается между разными revision; (5) прежний wizard Save/Back regression сохранён. Добавлять проверки в существующий owner spec.

### W5-02 — P1: обещанная recovery-копия другой ревизии теряется при следующем редактировании
Файлы: `use-product-story-editor.ts:216–240,249–264,350–354`.
restore оставляет несовместимый draft под account/product key и показывает notice, но persistDraft пишет в тот же key; успешный save очищает его. Никакой отдельной сохранённой recovery-копии нет.
Воспроизведение: положить draft другой revision с «RECOVERY TEXT» → открыть текущую → notice виден → добавить новый текст → 500ms. Во всём localStorage старого текста больше нет. Дополнительный тест красный.
Целевое решение: разделить активные story drafts по account/product/revision. Legacy-запись без revision сохранить в отдельном recovery namespace, не применять автоматически. Перенос старой записи выполнять copy→подтверждение записи→удаление источника; при quota источник остаётся. Очистка подтверждённого save удаляет только активную revision, logout — все записи аккаунта, включая recovery. В notice дать понятное действие выгрузки/копирования сохранённого текста; не обещать восстановление, требующее DevTools. Автоматическое слияние ревизий вне MVP.
Критерии: новая revision продолжает сохранять ввод, старая raw-копия остаётся после edit/save/reload; отказ записи при миграции ничего не удаляет; logout удаляет обе; при отсутствии storage никаких recovery-обещаний.

### W6-01 — P2: DR-03 исправлен только на initial probe
Файлы: `local-form-restore.ts:121–124`, `use-product-story-editor.ts:239`, `AuthorApplicationAchievements.tsx:247`, `lib/local-form-draft.ts:24–29,42–45`.
Результаты 'unsupported' и 'failed' разделены в типе, но три writer caller трактуют любой результат кроме 'ok' как ошибку. Без localStorage после ввода появляется предупреждение «не удалось сохранить…». Это воспроизведено в hook-тесте с отсутствующим storage. Кроме того, getter localStorage, бросающий SecurityError в браузере, превращается storage() в null и probe сообщает unsupported — это другой случай, его надо отличать от native.
Решение: единообразно отображать warning только для failed; unsupported не обещает поддержку browser drafts. В storage-adapter различать отсутствие API и ошибку доступа к существующему API. Не добавлять native storage.
Критерии: отсутствующий storage + edit/flush у всех трёх writers → нет warning; браузерный getter/setItem throwing → failed/warning; последующая успешная запись снимает ошибку только своего writer. Тест на unsupported должен включать ввод, initial mount недостаточно.

Дополнительные проверки выполнены в `/private/tmp/bidplace-story-review/wave-review.spec.ts` с `/private/tmp/bidplace-story-review/wave.config.mjs`: 3/3 намеренных регрессионных assertions красные (0.81s), конкретные последовательности приведены выше. Они проверяют текущие production hooks, не копию реализации. Это hook-level воспроизведение; полный браузерный пользовательский сценарий не запускался.
