# Правила для исполнителя и ревьюера волн запуска

Действуют поверх `AGENTS.md` (он главнее). Файл волны — план реализации в
формате superpowers `writing-plans`; этот файл — общий порядок работы. Механика
продаж — только [COMMERCE.md](COMMERCE.md).

## 1. Как устроен файл волны

| Раздел | Что в нём |
| --- | --- |
| Шапка | Goal, Architecture, Spec, ветка, коммит проверки фактов, зависимости |
| Global Constraints | Требования на всю волну; каждая задача их неявно включает |
| Review Focus | Пять сбоев, которые скорее всего ударят по пользователю; у каждого есть тест в задаче-владельце |
| Facts | Проверенные факты кода: символы, пути, строки-подсказки |
| Бэкенд / Фронтенд | Задачи `Task N`. У каждой: **Files** (Create / Modify / Test), **Reuse** (что взять готовым), **Interfaces** (Consumes / Produces — точные сигнатуры), шаги-чекбоксы |
| Промпт исполнителю | Копируется как есть |
| Промпт ревьюеру | Копируется как есть; инварианты и красные флаги |

Шаг в задаче — одно действие с проверяемым результатом. Код в плане — только
сигнатуры, тесты и утверждения; тела функций пишет исполнитель.

## 2. Перед работой

1. Прочитай `AGENTS.md`, этот файл, файл волны целиком, затем только разделы
   владельцев, на которые ссылается волна.
2. Скиллы проекта: `implement`; API — `nest`; ставки, заказы, контакты, жалобы,
   админ, письма, файлы — `security`; `apps/mobile` — `bidplace-ui`, затем
   `bidplace-ui-review`. Структурный поиск — `codebase-memory` с проверкой
   покрытия, иначе `rg`.
3. Скиллы superpowers (`~/.claude/skills`): исполнение — `subagent-driven-development`
   (свежий субагент на задачу + ревью после каждой) или `executing-plans`
   (всё в одной сессии + финальное ревью); `test-driven-development`;
   `verification-before-completion` перед любым «готово»; ревьюер —
   `requesting-code-review` / `receiving-code-review`. Сохраняй план там, где он
   лежит (`docs/launch/waves/`), не копируй в `docs/superpowers/`.
4. Факты в файле волны проверены на указанном коммите. Перед каждой задачей
   найди символ заново. Если факт неверен — запиши в журнал волны, цель не меняй.
5. Ветка — из шапки волны, от основной ветки. Один коммит на задачу, короткое
   сообщение в нижнем регистре, без упоминания агентов.

## 3. Решения по ходу и когда остановиться

Технические неясности (имя, место файла, выбор между двумя равными вариантами,
дефект плана с очевидным исправлением) решай сам и записывай в отчёт строкой
`Ruling: <что решил> — <почему> — <чего стоит ошибка>`. Не жди человека.

Остановись на текущей задаче и опиши причину, только если:

- нужно решение основателя: продукт, юридические формулировки, дизайн,
  защищённые документы (`AGENTS.md`, раздел Product and documentation);
- макета экрана нет или он противоречит `COMMERCE.md` — не собирай экран по
  догадке: явно напиши основателю «Пришлите экран <название> (Figma или
  скрин) или скажите собирать без макета», пометь `NEEDS-FIGMA` и продолжай
  другие задачи до ответа;
- действие необратимое, затрагивает безопасность или выходит за ветку
  (push, merge, deploy, удаление данных вне disposable БД);
- критерий приёмки недостижим без изменения цели;
- нужен секрет, внешний аккаунт или ручное действие.

## 4. Как писать код

- Сначала найди существующее: компонент, токен, хук, сервис, схему контракта,
  тестовый хелпер. Новое создаётся только там, где его называет **Files: Create**.
- Одно место правды: форматы и лимиты — `packages/contracts`; переходы статусов —
  в одном модуле домена; ключи кэша — в одной фабрике; цвета и размеры — токены.
- Один владелец на каждую логику — таблица «Владельцы логики» в
  [10-CODE-ARCHITECTURE.md](../product/10-CODE-ARCHITECTURE.md). Нужна логика из
  таблицы — вызывай владельца, не пиши копию. Новая тема — один файл
  именованных функций на тему (как утилитный класс в Java) или Nest-сервис, если
  нужны состояние или БД; никаких разрозненных хелперов по экранам и
  контроллерам. Существующие файлы не переписывать ради стиля — только то, что
  трогает задача.
- Маршруты, контроллеры и экраны тонкие. Логика — сервисы, функции домена, хуки.
- Никаких абстракций, опций и кода «на будущее», которых нет в **Interfaces**.
  Точки расширения — обычные функции и значения enum, не пустые интерфейсы.
- Запрещено: `any`, `@ts-ignore`, `@ts-expect-error`, отключение lint, пустые
  `catch`, тихие фолбэки, ослабление тестов, ретраев и таймаутов.
- Время сделки считает сервер (время БД в транзакции). Клиентским часам не доверяем.
- Деньги — целые числа в минимальных единицах + валюта.
- Удаление ставшего ненужным кода — часть задачи.
- Секреты и `.env` не читать.

## 5. Тесты

- TDD: сначала падающий тест из шага задачи, потом код, потом зелёный прогон.
- Расширяй существующие owner-спеки; новый файл — только если он есть в **Files**.
- Тестируй поведение и инварианты (результат в БД, ответ API, что видит
  пользователь), а не вызовы внутренних функций. Похожие случаи — `it.each`.
- Гонки, права, транзакции — интеграционные тесты на disposable БД `bidplace_e2e`.
- Сокращение тестов — только по списку волны. Тесты из «не трогать» не трогать.

## 6. Отчёт исполнителя

1. Итог одной фразой: сделано / частично / остановлено.
2. По задачам: что сделано, коммит, +/− строк.
3. Фактический вывод всех обязательных проверок (команда → результат).
4. Строки `Ruling:` и расхождения с фактами волны.
5. Что не проверено и риски.
6. Обновлённые документы (`11-PROJECT-STATUS.md` и другие, если волна требует).

## 7. Ревью

Ревьюер получает этот файл, файл волны и ветку.

1. Сверь дифф со скоупом: нет ли лишнего, всё ли сделано (по списку задач).
2. Сам выполни команды приёмки и тесты; отчёту не верь.
3. Пройди Review Focus, инварианты и красные флаги волны.
4. Проверь согласованность имён и сигнатур между задачами (Interfaces).
5. Скиллы: `code-review-best-practices`, `requesting-code-review`, `security` для
   чувствительного, `bidplace-ui-review` для интерфейса.

Вердикт — список замечаний: **Блокер** (нарушен инвариант, критерий,
безопасность, данные), **Серьёзное** (будущая регрессия, дубль владельца, тест
проверяет не то), **Мелочь**. Итог: «вливать» / «вливать после блокеров» /
«переделать задачу N».

## 8. Перед деплоем в прод

Деплой делает только основатель. Любой агент, который готовит или проверяет
реальный прод-деплой, сначала проходит
[docs/ops/ENVIRONMENT.md](../ops/ENVIRONMENT.md) и первым пунктом ответа
перечисляет каждую незаданную или непроверенную переменную со ★ (имя и что
сломается — без значений). Отдельной строкой всегда: состояние `TICK_CRON`
(пусто — аукционы закрываются только пока контейнер не спит; при реальных
аукционах нужно `*/5 * * * *`).
