# Правила для исполнителя и ревьюера волн запуска

Действуют поверх `AGENTS.md` (он главнее). Файл волны — техническое задание;
этот файл — общий порядок работы. Механика продаж — только [COMMERCE.md](COMMERCE.md).

## 1. Перед работой

1. Прочитай `AGENTS.md`, этот файл, файл волны целиком, затем только разделы
   владельцев, на которые ссылается волна.
2. Скиллы: `implement`; для API — `nest`; для чувствительного (ставки, заказы,
   контакты, жалобы, админ, письма, файлы) — `security`; для `apps/mobile` —
   `bidplace-ui`, затем `bidplace-ui-review`. Структурный поиск —
   `codebase-memory` с проверкой покрытия, иначе `rg`.
3. Факты в файле волны проверены на указанном коммите. Номера строк — подсказка.
   Перед каждым пакетом найди символ заново. Если факт неверен — исправь в
   отчёте, цель пакета не меняй.
4. Ветка: `feature/<короткое-имя>` или `fix/<короткое-имя>` от основной ветки
   (после W0 — `main`). Один коммит на пакет работ, короткое сообщение в нижнем
   регистре, без упоминания агентов.

## 2. Как писать код

- Сначала найди существующее: компонент, токен, хук, сервис, схему контракта,
  тестовый хелпер. Новое создаётся только там, где файл волны это разрешает.
- Одно место правды: форматы и лимиты — `packages/contracts`; переходы статусов —
  в одном модуле домена; ключи кэша — в одной фабрике; цвета/размеры — токены.
- Маршруты, контроллеры и экраны тонкие. Логика — сервисы, use-case функции, хуки.
- Не добавляй абстракции, опции и код «на будущее», если волна их не требует.
  Точки расширения, которые требует волна, — это обычные функции и значения
  enum, не пустые интерфейсы.
- Запрещено: `any`, `@ts-ignore`, `@ts-expect-error`, отключение lint, пустые
  `catch`, тихие фолбэки, ослабление тестов, ретраев и таймаутов.
- Время сделки считает сервер в транзакции. Клиентским часам не доверяем.
- Деньги — целые числа в минимальных единицах (копейки) + валюта.
- Удаление ставшего ненужным кода — часть задачи.
- Секреты и `.env` не читать. Push, merge, deploy не делать.

## 3. Тесты

- Расширяй существующие owner-спеки. Новый файл — только если волна его называет.
- Тестируй поведение и инварианты, а не устройство кода. Похожие случаи —
  `it.each`.
- Гонки, права, транзакции — интеграционные тесты на disposable БД
  `bidplace_e2e`. Не сбрасывай чужие БД.
- Сокращение тестов: только в области волны, только по списку волны или с
  объяснением в отчёте (дубль / проверка реализации / геометрия без смысла).
  Тесты из списка «не трогать» не трогать.

## 4. Когда остановиться

Остановись на текущем пакете и опиши причину, если:

- критерий приёмки недостижим без изменения цели;
- нужно решение основателя (продукт, юридические формулировки, дизайн);
- макет отсутствует или противоречит `COMMERCE.md` — пометь `NEEDS-FIGMA`;
- требуется секрет, внешний аккаунт или ручное действие.

## 5. Отчёт исполнителя

1. Итог одной фразой: сделано / частично / остановлено.
2. По пакетам: что сделано, коммит, +/− строк.
3. Фактические результаты всех обязательных проверок (команда → результат).
4. Расхождения с фактами файла волны.
5. Что не проверено и риски.
6. Обновлённые документы (`11-PROJECT-STATUS.md`, архитектура, дизайн-статус,
   журнал решений — только если волна требует).

## 6. Ревью

Ревьюер получает этот файл, файл волны и ветку. Порядок:

1. Сверь дифф со скоупом: нет ли лишнего и всё ли сделано.
2. Проверь каждый критерий приёмки сам (команды, `rg`, тесты), не верь отчёту.
3. Пройди инварианты и красные флаги из §9 файла волны.
4. Скиллы: `code-review-best-practices`, `security` для чувствительного,
   `bidplace-ui-review` для интерфейса.

Вердикт — список замечаний с уровнем:

- **Блокер** — нарушен инвариант, критерий, безопасность, данные; вливать нельзя.
- **Серьёзное** — будущая регрессия, дублирование владельца, тест проверяет не то.
- **Мелочь** — имена, читаемость.

И итог: «вливать» / «вливать после блокеров» / «переделать пакет N».
