# Продажи на bidplace — механика, данные, гонки

Единственный владелец правил продаж для волн W1–W7. Решения основателя —
`DEC-149` (в [12-DECISION-LOG.md](../product/12-DECISION-LOG.md)); здесь — как они
устроены. Если код или макет расходится с этим файлом — прав этот файл, а
расхождение записывается в отчёт волны.

## 1. Принципы

- bidplace — технологический посредник. Деньги и доставку не трогает: оплату и
  передачу автор и покупатель согласуют напрямую. Мы фиксируем договорённость,
  открываем контакты и храним историю.
- Не азартная игра: участие бесплатное, случайности нет, ставка — предложение
  купить по указанной цене. Слова «розыгрыш», «лотерея», «приз», «выигрыш» в
  интерфейсе и письмах запрещены. Вместо «Вы выиграли» — «Ваша ставка лучшая —
  работа ваша».
- Как конструктор: работа существует сама по себе; лот — временное предложение
  её продать. Лот можно снять и выставить заново, но не менять на ходу.
- Меньше статусов: всё, что можно вычислить из времени и связей, вычисляется.
- Сервер — единственный источник цены, времени и статуса. Клиент только показывает.

## 2. Сущности

| Сущность | Что это | Таблица |
| --- | --- | --- |
| Работа | Одобренная работа автора (портфолио). Без лота — просто в портфолио | `products` |
| Лот | Предложение продать работу: фиксированная цена или аукцион | `listings` (+ `auction_rules`) |
| Ставка | Неотменяемое предложение купить по сумме | `bids` |
| Заказ | Договорённость конкретного покупателя с автором о конкретной работе | `orders` |
| Жалоба | Обращение к администрации; на запуске — только по заказу | `reports` |
| Настройки уведомлений | Необязательные письма пользователя | `user_notification_settings` |
| Письмо в очереди | Обязательное или включённое письмо, отправляется тиком | `notification_outbox` |
| Избранное | Работы, отмеченные пользователем | `favorite_works` |

Пользовательских страниц «лот» нет: лот — блок на странице работы.

## 3. Лот

### 3.1 Создание

Только автор, только для своей работы, если одновременно:

- автор `APPROVED`, пользователь `active`, почта подтверждена;
- работа `APPROVED` (не скрыта), есть опубликованная ревизия;
- нет другого лота `SCHEDULED`/`LIVE` и нет открытого заказа (`OFFERED`/`ACTIVE`) по работе;
- нет завершённого заказа (`COMPLETED`) по работе — проданная работа не продаётся повторно.

Модерации лота нет: модерацию прошли работа и автор. Админ может снять лот.

Поля:

| Поле | Фиксированная цена | Аукцион |
| --- | --- | --- |
| `currency` | `BYN` или `RUB` | `BYN` или `RUB` |
| `priceMinor` | цена, > 0 | — |
| `startPriceMinor` | — | стартовая цена, > 0, кратна шагу |
| `startsAt` | сейчас | сейчас или позже, не дальше 30 дней |
| `endsAt` | нет (до покупки или снятия) | `startsAt` + от 1 до 14 дней |
| `contactWindowHours` | 1, 6, 24, 48 или 72; по умолчанию 24 | то же |

Срок связи выбирает автор: столько времени сторонам даётся связаться после брони.
Он виден в блоке лота («Срок связи после покупки — 24 часа») и в подтверждении
ставки и покупки: покупатель соглашается с ним вместе с «Правилами сделок».
Свободного ввода и сроков больше 3 суток нет.

Деньги — целые копейки (`Int`, минимальные единицы), без конвертации валют.
Верхний предел суммы — 100 000 000 минимальных единиц (1 000 000 BYN/RUB).

### 3.2 Статусы лота

| Статус | Значение | Как попадает |
| --- | --- | --- |
| `SCHEDULED` | Аукцион ждёт начала | создан с `startsAt` в будущем |
| `LIVE` | Идёт продажа | создан сразу или наступил `startsAt` |
| `ENDED` | Продажа закончилась (куплен, аукцион завершён со ставками или без) | покупка, тик по `endsAt` |
| `CANCELLED` | Снят автором (до первой ставки) или админом | действие |

Время главнее записанного статуса. Функция домена
`effectiveListingState(listing, now)` возвращает фактическое состояние:
`SCHEDULED` с `startsAt <= now` — это `LIVE`; `LIVE` с `endsAt <= now` — это
«завершён, итоги подводятся». Чтения используют её; запись статуса делает тик
(W2) и действия. Поэтому неважно, спал ли контейнер.

Публичная метка на работе — из лота и заказа:

| Ситуация | Метка |
| --- | --- |
| Лот `LIVE`, фиксированная цена | «Купить за N» |
| Лот `LIVE`, аукцион | текущая цена, ставок, осталось времени |
| Лот `SCHEDULED` | «Аукцион начнётся DD.MM в HH:MM» |
| Открытый заказ (`OFFERED`/`ACTIVE`) | «Забронировано» |
| Заказ `COMPLETED` (подтвердил автор или админ) | «Продано» |
| Нет лота / снят / заказ не состоялся | ничего (портфолио) |

«Продано» ставит только подтверждение автора (или админ по спору), не таймер:
фейковая покупка конкурента не может навсегда снять чужую работу с продажи.

### 3.3 Снятие и изменения

- Лот не редактируется. Изменить цену или сроки = снять и создать новый.
- Фиксированная цена: автор снимает в любой момент до покупки.
- Аукцион: автор снимает только пока нет ставок. После первой ставки — только админ.
- Админ снимает любой лот (`CANCELLED`, `cancelReason = ADMIN_REMOVED`); заказ
  при этом не создаётся, участники получают письмо «аукцион остановлен».
- Пока есть лот или открытый заказ, работу нельзя скрыть, изменить, удалить
  (`PRODUCT_IN_SALE`, хелпер `assertProductNotInSale` из W1).

## 4. Аукцион

### 4.1 Ставка

Условия (проверяются в одной транзакции, время — `now()` базы):

- пользователь `active`, почта подтверждена, не автор работы, не админ, не заблокирован
  для покупок (§7), у него < 3 броней (§7);
- в профиле есть телефон или хотя бы один из Telegram / Instagram / VK
  (`BUYER_CONTACTS_REQUIRED`; интерфейс ведёт на заполнение контактов);
- лот фактически `LIVE` (`startsAt <= now < endsAt`);
- пользователь не лидер сейчас (поднимать свою же ставку нельзя — `BID_ALREADY_LEADING`);
- сумма ≥ минимальной: без ставок — `startPriceMinor`, иначе текущая цена + шаг;
- сумма ≤ верхнего предела и кратна минимальной единице шага;
- принята текущая версия «Правил сделок» (`DEAL_RULES_NOT_ACCEPTED`, W6; то же для покупки,
  принятия предложения и создания лота).

Шаг — минимальное повышение; ставить можно любую сумму выше минимума, кратную
минимальной единице шага. Шаг зависит от текущей цены и валюты. Таблица — одна, в
`packages/contracts`:

| BYN, текущая цена меньше | шаг | RUB, текущая цена меньше | шаг |
| --- | --- | --- | --- |
| 25 | 0,50 | 500 | 10 |
| 100 | 1 | 2 500 | 25 |
| 500 | 5 | 10 000 | 100 |
| 1 000 | 10 | 25 000 | 250 |
| выше | 25 | выше | 500 |

Граница строгая: ровно 25,00 BYN — уже шаг 1. BYN — из `archive/commerce-v1`
(`DEC-039`); RUB — подтверждено основателем 2026-10-29.

Ставку можно сделать больше минимальной. Если сумма больше минимальной более
чем вдвое, интерфейс просит подтвердить («Вы ставите 500 BYN, минимальная — 120 BYN»).

### 4.2 Продление в конце

Если ставка пришла, когда до `endsAt` осталось ≤ 60 с, `endsAt` становится
`now + 60 с`, но не позже `originalEndsAt + 600 с`. Числа хранятся в
`auction_rules`, логика — одна чистая функция `resolveSoftCloseEndsAt` (есть в
архиве, перенести с тестами).

### 4.3 Идемпотентность

Клиент шлёт `idempotencyKey` (тот же regex, что в W0). Уникальность —
`(listing_id, bidder_user_id, idempotency_key)`. Повтор с тем же ключом и той же
суммой возвращает исходную ставку; с другой суммой — `IDEMPOTENCY_KEY_REUSED`.

### 4.4 Завершение

Тик (W2) вызывает `closeEndedListings(now)`: для каждого лота `LIVE` с
`endsAt <= now` в отдельной транзакции `closeListing(tx, listingId)`:

1. блокировка строки работы, условный переход `LIVE → ENDED` (`count === 1`, иначе уже закрыт — выйти);
2. есть ставки → заказ `ACTIVE` для лучшей ставки (`source = AUCTION_WIN`);
3. письма в очередь: покупателю «Ваша ставка лучшая», автору «Аукцион завершён»
   (или «без ставок»).

Ставка после `endsAt` отклоняется (`LISTING_NOT_OPEN`) даже если тик ещё не
прошёл. Победитель видит заказ после ближайшего тика: пока контейнер не спит —
≤ 30 с; спит и Cron выключен (`TICK_CRON` пусто, по умолчанию) — в первые 30 с
после любого визита; Cron `*/5` — ≤ 5 мин (W2). До этого страница показывает
«Аукцион завершён, подводим итоги». Срок связи считается от создания заказа.

### 4.5 Следующему участнику

Автоматической передачи победы нет: люди могли договориться вне площадки и не
отметиться, и система не должна бесконечно выбирать нового победителя. Если заказ
по аукциону `FAILED` по вине покупателя или покупатель отказался, автор видит две
кнопки: «Предложить следующему» и «Выставить снова» (новый лот, §3.1). Пока он не
выбрал, работа без метки (портфолио).

«Предложить следующему» создаёт заказ `OFFERED` (`source = SECOND_CHANCE`) для
следующего участника по его лучшей ставке:

- кандидаты — разные участники лота по убыванию их максимальной ставки (без
  аннулированных, §7), кроме тех, кому уже предлагали, и заблокированных для покупок;
- всего не больше двух предложений на лот (2-й и 3-й участник);
- предложение действует срок связи лота: «Принять» → `ACTIVE`; «Отказаться» или
  истекло → `FAILED` (`OFFER_DECLINED` / `OFFER_EXPIRED`, без вины);
- принять нельзя при 3 бронях, без контактов или при блокировке.

## 5. Фиксированная цена

«Купить» → подтверждение («Вы бронируете работу за N. Оплату и передачу вы
согласуете с автором напрямую») → в одной транзакции:

1. блокировка строки работы; лот фактически `LIVE`, условия покупателя как у ставки;
2. заказ `ACTIVE` (`source = FIXED_PURCHASE`, сумма = `priceMinor`);
3. лот `LIVE → ENDED` условно;
4. письма в очередь обоим.

Две одновременные покупки: вторая получает `LISTING_NOT_OPEN` (блокировка
строки + частичный уникальный индекс «один открытый заказ на работу»).

Если заказ по фиксированной цене `FAILED` (любая причина), лот в той же
транзакции условно возвращается `ENDED → LIVE` (`endedAt = null`): работа сразу
снова в продаже по той же цене. Автор может снять её обычным образом.

## 6. Заказ

### 6.1 Статусы

| Статус | Значение | Метка в интерфейсе |
| --- | --- | --- |
| `OFFERED` | Предложение следующему участнику ждёт ответа (срок связи лота) | «Предложено» |
| `ACTIVE` | Покупатель определён, стороны связываются | «Ждёт связи» |
| `COMPLETED` | Сделка состоялась (подтвердил автор или админ по спору) | «Состоялась» |
| `FAILED` | Не состоялась, с причиной | «Не состоялась: <причина>» |

Переходы — одна таблица в модуле заказа:

| Из | В | Кто | Условие |
| --- | --- | --- | --- |
| `OFFERED` | `ACTIVE` | покупатель | до `offerExpiresAt`, < 3 броней, контакты есть, не заблокирован |
| `OFFERED` | `FAILED` (`OFFER_DECLINED`) | покупатель | — |
| `OFFERED` | `FAILED` (`OFFER_EXPIRED`) | система | `offerExpiresAt <= now` |
| `ACTIVE` | `COMPLETED` | автор | — |
| `ACTIVE` | `FAILED` (`BUYER_REFUSED`) | покупатель («Отказаться от покупки») или автор | покупателю — подтверждение с последствием (§7) |
| `ACTIVE` | `FAILED` (`BUYER_NO_CONTACT`) | автор | `contactDeadlineAt <= now` |
| `ACTIVE` | `FAILED` (`BUYER_INVALID_CONTACTS`) | автор | `contactDeadlineAt <= now` |
| `ACTIVE` | `FAILED` (`SELLER_REFUSED`) | автор | — |
| `ACTIVE` | `COMPLETED` / `FAILED` (любая причина) | админ | разбор жалобы |
| `COMPLETED` / `FAILED` | `FAILED` / `COMPLETED` | админ | разбор жалобы: смена исхода, `reason` обязателен |

`contactDeadlineAt = activatedAt + contactWindowHours` лота. Автоматических
переходов у `ACTIVE` нет: исход отмечает автор (или админ по спору); тик только
напоминает (§6.3). `FAILED` и `COMPLETED` для участников конечные; админ может
сменить исход и «чья вина» (снять страйк, §7). Заказы не удаляются никогда — ни
автором, ни покупателем (защита от фиктивных покупок, скрывающих работу).
После `FAILED`: фиксированная цена — лот снова `LIVE` (§5); аукцион — выбор
автора (§4.5).

Вина по причине: `BUYER_REFUSED`, `BUYER_NO_CONTACT`, `BUYER_INVALID_CONTACTS` →
покупатель; `SELLER_REFUSED` → автор; `OFFER_*`, `ADMIN_CANCELLED` → нет. Хранится
в `faultSide`, чтобы админ мог исправить.

### 6.2 Что видно в заказе

| Поле | Кто видит |
| --- | --- |
| Номер заказа (`publicId`, 11 символов `PublicIdService`, напр. `q7Xf2_Kd9aB`) | оба, админ |
| Код сделки (6 цифр) — назвать друг другу при связи | оба, админ |
| Работа: название, обложка, автор (снимок на момент заказа) | оба, админ |
| Сумма и валюта, способ (аукцион / фикс / следующему) | оба, админ |
| Контакты покупателя: подтверждённая почта + телефон / Telegram / Instagram / VK | автор, админ |
| Контакты автора: то же | покупатель, если у автора включено «Показывать мои контакты покупателю»; админ — всегда |
| Комментарий покупателя (≤ 500, при покупке/принятии) | оба, админ |
| Заметка автора (≤ 1000) | только автор, админ |
| Срок связи и когда можно отметить «не вышел на связь» | оба |
| Подсказка: «bidplace не принимает оплату. Не переводите деньги, пока не договорились с автором» | покупатель |
| Кнопки по таблице 6.1, «Пожаловаться», «Поддержка», «Чек» | по ролям |

Контакты берутся из профиля в момент чтения (не снимок): исправленный телефон
сразу виден второй стороне. После `FAILED` контакты **не** скрываются: они
нужны для разбора спора, а увести сделку в обход площадки через них нельзя —
они появляются только после брони. Смена контактов требует входа не старше
5 минут и отправляет владельцу письмо «Контакты изменены» (`CONTACTS_CHANGED`):
украденная сессия не должна тихо подменить телефон в открытых сделках.

Автор может выключить «Показывать мои контакты покупателю» (настройка профиля,
по умолчанию включена) — например, публичный человек связывается сам. Тогда
покупатель видит «Автор свяжется с вами сам в течение <срок связи>».

Чек — подтверждение сделки, не кассовый документ (деньги площадка не принимает).
Появляется только у `COMPLETED`: номер заказа, код сделки, работа, автор, имя
покупателя, сумма, дата; без контактов; внизу «Не является кассовым чеком».
Обе стороны получают письмо «Сделка состоялась» с этими данными и ссылкой на
заказ; в заказе кнопка «Чек» открывает карточку и сохраняет PNG (рисуется на
клиенте, W5, [SHARE-EXPORT.md](SHARE-EXPORT.md)). Отдельного серверного документа
нет; публичная проверка чека по коду — после запуска.

### 6.3 Напоминания и «Требует внимания»

Автозакрытия нет. Пока `ACTIVE` заказ без отметки автора, тик:

- через 24 ч после `activatedAt` — письмо автору «Отметьте, состоялась ли сделка»;
- через 48 ч — второе такое письмо;
- через 72 ч — заказ попадает в список «Требует внимания» у админа
  (`GET /api/admin/attention`), статус не меняется; основатель связывается с
  автором ([OPERATIONS.md](OPERATIONS.md)).

Повторы не дублируются: `orders.sellerRemindersSent` (0–2) меняется условно.

## 7. Защита от срыва и обмана

Все решения «может ли пользователь действовать» принимает один модуль
`apps/api/src/antifraud/` (волна [W2b](waves/W2b-antifraud.md)); продажи и вход
только спрашивают его (`assertCanBid(tx, …)`, `assertCanPurchase`, …) и сообщают
факты (`recordStrike`, сигналы). Правила ниже — его контракт.

| Правило | Как |
| --- | --- |
| Не больше 3 броней у покупателя | считаются активные заказы **и** аукционы, где он сейчас лидер; при 3 ставка, покупка и принятие отклоняются (`BUYER_ORDER_LIMIT`). Так нельзя «выиграть» десять аукционов разом |
| Страйк покупателя | каждый `FAILED` с `faultSide = BUYER` и `strikeVoidedAt = null`. Отказ самого покупателя — сразу. Если `FAILED` отметил автор — страйк начинает считаться через 72 ч и не считается, пока по заказу открыта жалоба покупателя |
| Блокировка покупок | ≥ 2 страйка → ставки, покупки, принятие запрещены (`BUYER_BLOCKED`) до решения админа (снять страйк). Перед «Отказаться от покупки» покупатель видит: «Вы получите страйк. После 2 страйков ставки и покупки блокируются» |
| Временный автоблок | ≥ 2 сигнала **разных** видов за 24 ч → ставки и покупки приостановлены (`BUYER_BLOCKED`, причина `FRAUD_REVIEW`), случай — в «Требует внимания» у админа. Один сигнал — только запись. Виды: проваленная невидимая проверка Turnstile; серия ставок по разным лотам быстрее человека; общий браузер с автором лота; аккаунт моложе суток со ставками в серии. Пороги — в W2b |
| Бан | админ ставит аккаунту `User.status = banned` одной кнопкой с причиной (`SellerProfile.SUSPENDED` — отдельный статус автора, автоматически не связан; проект `DEC-152`, требуется подтверждение основателя). Ставки пользователя в идущих аукционах аннулируются (`bids.voidedAt`, история остаётся), цена и лидер пересчитываются по оставшимся ставкам (нет ставок → стартовая цена); завершённые заказы не трогаются — их разбирают жалобой. С момента бана по лотам забаненного продавца нельзя ставить, покупать и создавать заказы, в том числе тиком; сами лоты снимает админ отдельно, действующие заказы разбираются вручную |
| Страйк автора | жалоба по заказу признана (`UPHELD`) с виной автора. На запуске — только сигнал для админа; блокировка автора — `SUSPENDED` вручную |
| Нельзя покупать у себя | автор не ставит и не покупает свою работу |
| Частота | ставки — 10 в минуту на лот; жалобы — 5 в час на пользователя. Счётчики в базе (W2b), переживают рестарт |
| Удаление | заказы, ставки и жалобы не удаляются; удаление аккаунта (`DEC-123`) обезличивает, но не стирает их |

Невидимый Turnstile (без интерфейса) проверяет покупку и первую ставку в сессии;
провал — только сигнал, не отказ. На регистрации тот же невидимый режим, но
проверка остаётся обязательной (как сейчас): провал → «Попробуйте ещё раз».

`getTrustSignals(userId)` — одна функция, только реальные факты, без
рейтингов-заглушек:

```ts
type TrustSignals = {
  completedAsSeller: number; completedAsBuyer: number
  buyerStrikes: number; sellerFaultFailures: number
  upheldReportsAgainst: number; memberSince: Date; emailVerified: boolean
}
```

На запуске показывается админу (заказ, жалоба, пользователь) и автору в карточке
заказа («3 состоявшиеся покупки»). Публичный рейтинг и отзывы — после запуска,
поверх этих же фактов.

## 8. Жалобы и поддержка

Таблица `reports` общая на будущее, интерфейс запуска — только по заказу.

| Поле | Значение |
| --- | --- |
| `targetType` | `ORDER` (запуск), `WORK`, `AUTHOR`, `USER` (позже) |
| `targetId` | id цели |
| `reporterUserId` | автор жалобы |
| `reason` | для заказа: `NO_CONTACT`, `TERMS_CHANGED`, `NOT_AS_DESCRIBED`, `NOT_HANDED_OVER`, `FRAUD`, `OTHER` |
| `text` | ≤ 1000 |
| `status` | `OPEN`, `UPHELD`, `REJECTED` |
| `faultSide` | при `UPHELD`: `BUYER` / `SELLER` / `NONE` |
| `adminNote`, `resolvedAt`, `resolvedById` | разбор |

- Пожаловаться может участник заказа в `ACTIVE`, `COMPLETED` (14 дней) и `FAILED`
  (14 дней) — в том числе покупатель после того, как автор отметил срыв.
- Одна открытая жалоба от участника на заказ (частичный уникальный индекс).
- Открытая жалоба покупателя замораживает его страйк по этому заказу.
- Вторая сторона получает письмо «По вашему заказу открыта жалоба» (без текста жалобы).
- Спор разбирается вручную, без отдельных экранов: заказ с открытой жалобой — в
  списке у админа с обеими сторонами и их контактами; основатель связывается с
  ними сам. Действия админа — только три: снять страйк, сменить исход
  (`COMPLETED`/`FAILED`), заблокировать пользователя; у каждого обязательна причина.
- «Поддержка» ведёт в Telegram поддержки и на почту для обращений. Ссылки —
  настройки окружения (`SUPPORT_TELEGRAM_URL`, `SUPPORT_EMAIL`), показываются в
  подвале, настройках и заказе ([MONITORING-AND-SUPPORT.md](MONITORING-AND-SUPPORT.md)).

```prisma
enum ListingType   { FIXED AUCTION }
enum ListingStatus { SCHEDULED LIVE ENDED CANCELLED }
enum ListingCancelReason { AUTHOR_WITHDREW ADMIN_REMOVED }

  voidedAt DateTime?; voidReason VarChar(40)?          // аннулирована баном (§7), не удаляется
  @@unique([listingId, bidderUserId, idempotencyKey]) @@index([listingId, amountMinor]) }
model Order {
  id; publicId VarChar(16) @unique; dealCode Char(6)
  productId; listingId; sellerUserId; buyerUserId
  source OrderSource; sourceBidId? @unique   // null для FIXED_PURCHASE
```

## 11. Гонки и защита

Общее правило: любое действие продаж — одна транзакция `ReadCommitted`, первым
шагом `lockProductRowForUpdate(productId)`; все записи статусов условные
(`updateMany where status in (...)` + `count === 1`); время — `now()` базы.
Блокировка строки работы сериализует всё по одной работе, не мешая другим.

| Сценарий | Что защищает | Тест (W3/W7) |
| --- | --- | --- |
| 50 ставок одновременно на один лот | блокировка работы; каждая видит актуальную цену; лишние — `BID_TOO_LOW` | интеграция: 50 параллельных, итог — цена = максимум, `bidCount` = числу принятых, ни одной потерянной |
| Ставка в последнюю секунду и тик закрытия | обе берут блокировку; кто второй — видит новый `endsAt` или `ENDED` | интеграция с двумя транзакциями |
| Два покупателя «Купить» | блокировка + `one_open_order_per_product` | второй — `LISTING_NOT_OPEN` |
| Автор снимает лот, а покупатель покупает | блокировка, условный переход | ровно одно действие проходит |
| Автор снимает аукцион, а приходит первая ставка | проверка `bidCount = 0` под блокировкой | ровно одно |
| Повтор ставки после обрыва сети | idempotency-ключ | один ряд, тот же ответ |
| Два тика одновременно | условный `LIVE → ENDED`, уникальность `sourceBidId` | один заказ |
| Принятие предложения в момент истечения | сравнение с `now()` базы под блокировкой | ровно одно |
| Автор скрывает работу во время продажи | `assertProductNotInSale` (W1) | `PRODUCT_IN_SALE` |
| Лидер блокирован админом | блокировка покупок проверяется на ставке/покупке/принятии; уже выигранный заказ разбирает админ | — |
| Бан и ставка того же пользователя одновременно | бан аннулирует ставки под блокировкой каждой работы; ставка после бана — `BUYER_BLOCKED` | интеграция: цена и лидер = максимум по неаннулированным |
| Срыв фиксированной покупки и новая покупка | `FAILED` и `ENDED → LIVE` в одной транзакции под блокировкой | ровно один открытый заказ |
| Пользователь видит чужой заказ | все чтения заказа — `where buyerUserId = me OR sellerUserId = me` (или админ); 404, не 403 | интеграция по ролям |
| Утечка контактов | контакты только в ответе заказа участнику; в публичных ответах и логах их нет | проверка контрактов |

## 13. Чем вдохновлялись (hendis.ru)

Hendis — CRM мастера с витриной, денег не касается, аукционов нет. Берём:
статус наличия и «скрыть после продажи» (наша метка «Продано»), одну карточку
заказа с заметками и сроками, комментарий покупателя, контакты только после
заказа, ссылку на работу. Не берём: открытую регистрацию (у них в ленте курсы
и растения), публичные телефоны на витрине, «платформа не отвечает за споры»
(у нас жалоба по заказу), склад и производство как продукт, неформальные
«брони на 24 часа». Позже стоит взять: «на заказ» со сроком изготовления,
поле трек-номера, калькулятор себестоимости.

| C16 | Правила сделок публикуются на площадке без отдельного согласования с юристом |

## 15. Угрозы и где они закрыты

Подробные проверки — в задачах волн; здесь — карта.

| Угроза | Защита | Где проверяется |
| --- | --- | --- |
| Чужой видит контакты или заказ | 404 постороннему, контакты только участникам заказа (автора — по его настройке), не в публичных ответах и кэше Worker | W3 Task 4, 7 |
| Перебор номеров заказов и кодов | `publicId` 64 бита; код сделки `crypto.randomInt`, не принимается ни одним маршрутом | W3 Task 6 |
| Украденная сессия меняет контакты | вход не старше 5 минут + письмо владельцу | W3 Task 7 |
| Захват аккаунта через привязанный Google/Telegram | сброс пароля завершает сессии; привязанный вход остаётся — остаточный риск, разбор по OPERATIONS §3.8 | W3 Task 7 |
| Данные зрителя лота у следующего пользователя устройства | ключ лота под пользователем, чистится при выходе | W4 Task 1 |
| Фейковые покупки, призрачные победы | лимит 3 броней с учётом лидерства, обязательные контакты, «не вышел на связь» после срока автора, «Продано» только по подтверждению, срыв фиксированной цены возвращает работу в продажу | W3 Task 5, 7, 8 |
| Серия фейковых аккаунтов морозит работы автора | короткий срок связи по выбору автора; отказ сразу освобождает работу; страйки и блок; сигналы антифрода | W2b, W3 Task 5, 7 |
| Боты делают ставки | невидимый Turnstile + сигналы скорости; автоблок по 2 разным сигналам, бан аннулирует ставки | W2b, W3 Task 5 |
| Автор мстит покупателю страйками | задержка 72 ч, заморозка жалобой, снятие админом | W3 Task 7 |
| Ставки со второго аккаунта автора | сигнал «общий браузер с автором»; остальное — остаточный риск, жалобы и `getTrustSignals` | W2b, W3 Task 5 |
| Спам ставками и жалобами | лимиты частоты в базе, одна открытая жалоба | W2b, W3 Task 5, 9 |
| Инъекция заголовков в письмах | тема без CR/LF, письма только на подтверждённую почту | W3 Task 3 |
| Ошибки и злоупотребления админа | причина обязательна, `auditEvent` с прежним и новым значением | W3 Task 7, 9 |
| Приватные фото истории в карточке шаринга | в карточку идёт только опубликованная публичная версия | W5 Task 2 |
| Внешний вызов тика | `/api/internal/*` снаружи 404, секрет, повтор безопасен | W2 Task 1–2 |
