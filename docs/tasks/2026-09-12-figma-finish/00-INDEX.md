## Практическое распределение моделей

- Самые сильные: author/work финальное совпадение, glass/frost, sticky transitions, shared компонентные решения и независимая приёмка.
- Sol high: filters/state wiring, shared modal, заявки и wizard с существующими API. Это не простая вёрстка: нужны корректные состояния и сохранение поведения.
- Terra: небольшие сборки экранов и конкретные layout исправления после принятия masters. Ограничить одним экраном/одной причиной, давать готовый source map.
- Grok 4.6 high / Composer 2.5: начать с07-home как пилота, затем08/09 только если пилот прошёл тот же visual gate. Не поручать им одновременно «весь дизайн» и менять общую систему эффектов.

Это распределение по риску задачи, а не доказанный рейтинг интеллекта моделей. Сравнения Sol/Terra с Grok/Composer на этом репозитории нет. Официально [Sol](https://developers.openai.com/api/docs/models/gpt-5.6-sol) позиционируется для сложной профессиональной работы, [Terra](https://developers.openai.com/api/docs/models/gpt-5.6-terra) — как баланс возможностей и стоимости. Проверять выбранную модель одним одинаковым пилотом, а не увеличением числа тестов. При отсутствии browser tools агент не может сам закрыть visual acceptance.

Сначала02-author и03-work как важнейшие экраны.04-cards — до масштабирования на каталоги.05-share и06-filters — следующим пакетом. Простые07–09 — после готовности masters.10–12 — отдельно, не смешивать с публичными экранами.13 — независимый финальный проход. Если важен быстрый запуск, форму reset/review без исходника не выдавать как задачу на pixel-perfect.

## Открытые входные материалы и исключения

Отдельное решение/кадр нужны для exact review, private handoff, phone verify/forgot/reset, содержимого delivery сверх RFC stub, лицензированных Geist assets и «Открытия недели». Live search требует API контракта. Commerce и POST_MVP captures не входят. Нативные iOS/Android не являются целью этой приёмки. Не заполнять эти пробелы фантазией; сохранять существующее поведение и явно обозначать границу.
