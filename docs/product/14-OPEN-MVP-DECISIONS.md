## D01 — предложение своей цены

Уже решено: offer бывает только у fixed sale; его включает автор; отправка offer
не является покупкой; принятие автором сразу создаёт сделку по принятой цене.

Нужно выбрать четыре правила:

1. **Срок:** 24 или 48 часов. Рекомендация для MVP — 48 часов.
2. **Отзыв покупателем:** разрешить до принятия автором либо запретить. Рекомендация —
   разрешить; accepted offer уже не отзывается этим действием.
3. **Counteroffer:** добавить сейчас либо оставить только `принять / отклонить`.
   Рекомендация — без counteroffer в MVP.
4. **Параллельная покупка:** сохранять fixed CTA активным либо резервировать Work под
   ожидающий offer. Рекомендация — не резервировать; первая атомарно созданная сделка
   закрывает Listing и аннулирует остальные offers.

Почему важно: это определяет Offer statuses, timestamps, конкурентные транзакции,
уведомления и тексты кабинета.

## D02 — победитель не выходит на связь

Текущий runtime хранит 48-часовой срок и допускает административную замену. Это
техническая реализация, а не утверждённое конечное правило.

Нужно выбрать:

1. Сколько ждать: 24, 48 или 72 часа. Рекомендация — 48 часов с in-app напоминанием.
2. Кто может объявить сделку несостоявшейся: только автор либо обе стороны.
   Рекомендация — любая сторона сообщает причину, но terminal failed требует
   подтверждения второй стороны или решения администратора; одностороннее действие
   не освобождает Work и не удаляет историю.
3. Нужен ли second chance. Рекомендация — отдельное предложение следующему участнику
   по его последней ставке на 24 часа; новая сделка возникает только после его
   подтверждения и только при подтверждённой причине на стороне победителя.
4. Если second chance не принят: автор перевыставляет Work новым Listing. Для MVP
   предложение отправляется только runner-up; автоматической цепочки нет.

Автоматически раскрывать автору контакты всех участников не следует: они участвовали
в другом результате и не подтверждали новую сделку.

## D03 — статусы связи и передачи

Нужно выбрать, кто меняет статусы после создания сделки.

Рекомендуемый минимальный вариант:

- `Ждём связь` создаётся сервером;
- `Связались` может отметить любая сторона;
- `Передача завершена` требует подтверждения обеих сторон либо остаётся
  `завершение заявлено`, пока вторая сторона не подтвердит;
- `Сделка не состоялась` требует причины и остаётся в истории;
- жалоба не меняет автоматически статус сделки.

Почему важно: эти действия влияют на репутацию, повторную продажу и возможные споры.

## D04 — старые Order snapshots

Новые Orders уже фиксируют название, валюту и identity. Старые строки с пустыми
snapshot-полями читают живой Product/Listing.

Перед появлением реальных изменяемых данных выбрать:

- подтвердить, что старые строки являются disposable test data, и очистить их перед
  запуском; это рекомендуемый вариант для текущего локального состояния;
- либо, если найдены реальные записи, выполнить проверяемый backfill из immutable
  источника. Копировать текущие изменяемые Product/Listing как исторический факт нельзя.
