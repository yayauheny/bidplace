# Product overview

Для дизайнера. Без маркетинговых формулировок и без предписания внешнего вида.

---

## Product idea

bidplace — **creator-first**. Цепочка продукта:

```text
автор → работа → история / авторство / происхождение / ценность → форма продажи → покупатель
```

Покупатель должен понять:

1. что это за работа;
2. кто сделал;
3. почему это единственное / ограниченное / связанное с человеком;
4. какой сейчас формат продажи и можно ли действовать.

Сейчас формат продажи — timed auction. Он не «создаёт хайп». Он честно определяет цену, когда ценность уже есть.

Другие форматы (фиксированная цена и далее) — направление после MVP, не текущий экран. См. [13-FUTURE-PRODUCT.md](./13-FUTURE-PRODUCT.md).

---

## Buyer

Человек, который готов смотреть работу и ставить реальные деньги в BYN.

До ставки достаточно смотреть всё публичное без аккаунта.  
Перед первой ставкой нужны: аккаунт, подтверждённый email, принятые правила сервиса.

После победы покупатель получает способ связаться с автором (или автор пишет покупателю) и договаривается об оплате и передаче **сам**.

---

## Creator

Человек, который продаёт **свою** физическую работу.

Известность не обязательна. Нужны готовые работы, история, готовность привести свою аудиторию и пройти ручную модерацию.

Второй тип продавца в продукте — «популярный человек с личной вещью». Это долгосрочная цель, не первый пилот. В текущих формах тип продавца всегда «автор»; отдельного сценария «инфлюенсер» нет.

---

## Core value proposition

Покупатель видит работу и человека, а не витрину лотов.  
Автор продаёт напрямую, без посредника и без искусственных ставок.  
История и происхождение — часть товара, не второстепенная подпись.

---

## Core actions

| Кто | Главные действия |
|---|---|
| Гость | Смотреть, искать, открыть работу/автора, перейти к входу |
| Покупатель | Поставить ставку, смотреть свои покупки/ставки, открыть заказ после победы |
| Автор (одобренный) | Создать работу, загрузить фото, заполнить историю создания, запланировать аукцион |
| Админ | Одобрить или вернуть на правки автора и работу; сопровождать срыв передачи |

Глобальное действие **Создать** ведёт гостя/не-автора в заявку, одобренного автора — к новой работе. Подробности: [08-AUTH-ACCOUNT-ROLES.md](./08-AUTH-ACCOUNT-ROLES.md).

## MVP boundaries

Пилот: Беларусь, русский язык, BYN, ручное одобрение.

Единственный формат продажи в MVP: **аукцион с стартовой ценой**. Нет скрытого резерва, нет «купить сейчас», нет другой валюты.

Не входит в MVP: платежи, доставка платформой, чат, избранное, подписка на автора, рекомендации, рейтинг, видео как обязательный формат, live-торги.

Старый MVP-документ (`05-MVP-RFC`) писал, что discovery «не входит». Позже это **пересмотрено**: публичные Главная / Работы / Авторы / Поиск — подтверждённая часть продукта. См. [11-DISCREPANCIES.md](./11-DISCREPANCIES.md).

## Current sale format

1. Автор создаёт работу и отправляет на модерацию.
2. После одобрения работы назначает начало, конец и стартовую цену.
3. До старта торги **запланированы** — ставить нельзя, страницу видно.
4. В окне торгов статус **идут** — можно ставить.
5. После конца — **завершены**. Победитель — высшая принятая ставка. Если ставок не было — продажа не состоялась.
6. Контакты открываются только сторонам этой сделки.

Время и минимальную ставку считает сервер, не клиентский таймер.

## Payment and delivery

Внутри bidplace **нет** оплаты и логистики.

На странице работы поле «передача / доставка» — свободный текст автора (самовывоз, договорённость и т.п.).  
Текущая подпись «Оплата и доставка» в интерфейсе показывает **тот же текст**, а не платёжный метод. Платёжного поля нет.

После победы:

- покупатель видит контакт автора **или**
- автор видит email покупателя —

в зависимости от настройки «кто пишет первым». Дальше люди договариваются сами.

Будущие платежи и доставка: [13-FUTURE-PRODUCT.md](./13-FUTURE-PRODUCT.md). Не проектировать checkout в MVP.

## Roles

| Роль | Кто это |
|---|---|
| Гость | Не вошёл |
| Пользователь / покупатель | Вошёл; может стать автором |
| Автор | Есть заявка SellerProfile. Продавать можно только со статусом «одобрен» |
| Админ | Модерация. **Не может** ставить ставки и не имеет раздела покупок |

Статусы заявки автора: на модерации → одобрен / нужны правки / отклонён / приостановлен.

## Navigation relationships

Доступные назначения (не раскладка шапки):

| Назначение | Куда | Кому |
|---|---|---|
| Главная | `/` | все |
| Работы | `/works` | все |
| Авторы | `/authors` | все |
| Поиск | `/search?q=…` | все |
| Создать | новая работа или заявка автора | не админ; видимость зависит от роли и поверхности — [08](./08-AUTH-ACCOUNT-ROLES.md) |
| Войти | `/login` | гость |
| Кабинет / заявка / стать автором | `/profile` | вошедший, по статусу заявки |
| Покупки | `/me/activity` | вошедший, не админ |
| Модерация | `/admin` | только админ |
| Выйти | — | вошедший |

В интерфейсе сейчас смешаны слова «Аукционы», «Работы», «предмет», «Стать продавцом». В исследованиях чаще «Стать автором». Единый словарь не утверждён — [12-OPEN-QUESTIONS.md](./12-OPEN-QUESTIONS.md).

## Main routes

| Экран | Адрес | Публичный? |
|---|---|---|
| Главная | `/` | да |
| Работы | `/works` | да |
| Авторы | `/authors` | да |
| Поиск | `/search?q=` | да |
| Работа | `/product/[id]` | да, если работа одобрена и есть публичный аукцион |
| Автор | `/seller/[slug]` | да, если автор одобрен |
| Вход / регистрация | `/login`, `/register` | да |
| Покупки | `/me/activity` | только вошедший, не админ |
| Заказ | `/order/[id]` | только стороны сделки и админ |
| Заявка / кабинет автора | `/profile` | вошедший |
| Новая работа | `/products/new` | одобренный автор |
| Редактирование работы | `/products/[id]` | владелец |
| Планирование аукциона | `/listings/new` | одобренный автор |
| Модерация | `/admin` | админ |

У страницы работы в текущей реализации три адресных вида: «О работе» (по умолчанию), `?tab=creation`, `?tab=bids`. Это **группировка данных в коде**, не требование к композиции макета. Дизайнер решает, как показать те же группы информации.

## Information that must stay understandable

Независимо от композиции:

- идентичность работы и текущее действие продажи должны быть понятны без догадок;
- автор должен быть достижим со страницы работы;
- история / происхождение / уникальность не должны пропадать за одной только ценой;
- гость должен понять, что ставка требует входа.

---

## What the designer should assume

- Реалистичные тексты — на русском, иногда длинные.
- Деньги — только BYN, с копейками.
- Пустые и сломанные фото обязательны: сервис не подставляет стоковые картинки.
- Нельзя вводить счётчики подписчиков, рейтинг, «verified», NFT, скидки, фейковый дефицит.
- Follow / save / video / фикс. цена / чат / колокольчик — не MVP UI. См. [13](./13-FUTURE-PRODUCT.md).
