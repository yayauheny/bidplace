# 02 · User journeys и варианты входа

**Статус:** предложения. Текущая схема подтверждена [design flows](../design/02-USER-FLOWS-AND-SCREENS.md) §§8–9, [MVP RFC](../product/05-MVP-RFC.md) §§8–10 и проверкой ProductsService.create (2026-11-03). Финальный вид экранов — только через Figma/решение основателя.

## Journey A — новый творческий автор

**Сейчас:** регистрация + email proof → заявка автора (photo → основная информация → контакты → о себе → достижения) → отправка → ожидание approval → Work wizard (сведения → фото → история → review) → модерация Work → публичная ссылка.

**Проблема:** долго до первого ощутимого результата. Необязательные блоки представлены как отдельные обязательные проходы; работа появляется только после повторного допуска.

**Предлагаемое улучшение для ближнего MVP:**

1. Вход/регистрация и email proof только там, где это действительно требуется контрактом.
2. **«Создать пространство» — короткая заявка в два визуальных блока** (не снижая серверный минимум): профиль (фото/публичное имя/slug/страна), творчество (краткий текст/направление), затем явная отправка и ожидание решения.
3. Контакты для публичного профиля, подробная практика и достижения — действие **«Дополнить позже»**, не пустые обязательные шаги. Не менять privacy-контракт приватных deal contacts.
4. Понятный pending screen: **«На проверке»**, что увидит автор и что можно делать пока ждёт; не обещать возможность Work, которой сервер не даёт.
5. Одобренный автор видит **«Добавить первую работу»** без возвращения в длинную анкету.
6. Создание Work: фото и название → нужное для review → предпросмотр → «Отправить на проверку».
7. После approval Work: **«Открыть страницу / Скопировать ссылку / Добавить следующую»**. Продажа необязательна.

**Важное уточнение:** два визуальных шага — не механический KPI. Проверить чтение/доступность/ошибки: если получается два гигантских полотна, допустить три коротких блока, но не возвращать отдельные «пустые» достижения.

## Зафиксированное разночтение между существующими документами

**RFC §10** уже описывает первым шагом «основные фотографии и название», а **Design Flows §9** описывает фактический wizard как «title/category/characteristics → images → story → review». Код review тоже подтверждает summary-first, не полноценный public preview. Это не основание сразу переписать экран: перед задачей нужно **прочитать live Figma, действующий route/wizard и уточнить owner**, затем либо привести реализацию к уже выбранному решению, либо явно пересмотреть flow. Не выдавать противоречие за утверждённый redesign.

## Journey B — возвращающийся автор

**Сейчас:** кабинет/список Works → editor или публичная работа → доступная форма продажи. Разрозненные состояния Work и Listing.

**Цель без нового API:** из списка — **«Добавить новую»** или контекстное действие по конкретной Work:

| Work + commerce state | Одно главное действие | Вторичное |
| --- | --- | --- |
| Не сохранён / локально несохранён | Продолжить, с честным предупреждением об unsaved media | Выйти |
| DRAFT | Продолжить | Удалить/закрыть в рамках текущего контракта |
| CHANGES_REQUESTED / REJECTED | Исправить замечания по полям | Посмотреть отзыв |
| PENDING_REVIEW | Смотреть статус и отправленную версию | Назад к списку |
| APPROVED, no Listing | Открыть и поделиться | Выставить на продажу |
| APPROVED, eligible for sale | Выставить | Изменить Work (с повторной модерацией) |
| LIVE/SCHEDULED Listing | Управлять продажей | Поделиться |
| ACTIVE/OFFERED order | Перейти к заказу | Смотреть Work |
| COMPLETED | Смотреть итог и Work | Поделиться историей без ложного платёжного доказательства |

Статусы публикации и торгов не смешивать в один badge. Подставлять реальные разрешённые действия и не скрывать причину, если продажа невозможна.

## Journey C — зритель пришёл по внешней ссылке

**Сейчас (спецификация):** публичная Work → фото/история/автор/related → share/QR; lot block по действующим состояниям.

**Предлагаемая очередность взгляда:**

- Above the fold: сильная фотография, понятное название/имя и доступное действие, если оно есть.
- В первые секунды понятно, что это оригинальная работа/личная вещь (по заявленным фактам автора, без необоснованных гарантий).
- Дальше детали и необязательная история, другие работы автора, переход к профилю.
- На Work без продажи **нет пустого Buy CTA**; остаются сохранение, поделиться, изучить.
- При продаже: сумма, валюта, время, последствия участия/контактное окно; на телефоне primary CTA не теряется после прокрутки (действующий lot/header contract сохранять).
- Возврат из Work сохраняет исходный список/позицию там, где навигационный стек существует; прямой URL без истории получает безопасный fallback.

**Отдельная проверка:** переход к другому автору — пользователь нашёл собственную пользу Bidplace или просто вернулся в TikTok? Данные пока не доказывают ответ.

## Journey D — покупатель ставит / бронирует

По текущему COMMERCE: видит Work и live Listing → открывает bid/buy sheet → auth/email proof при необходимости → контактные данные и антифрод-гейты → явное подтверждение ставки/покупки → состояние/заказ.

**UX инварианты:**

1. Нажатие на «Ставка» с гостевой сессией сохраняет **intent вернуться к Work** после auth, но **НЕ выполняет ставку автоматически**.
2. После входа перечитываются серверные цена, время, доступность, права; прежняя сумма не принимается молча.
3. Отдельный явный confirm с текущей ценой, валютой, сроком связи и последствиями; no duplicates при повторном клике.
4. Если лот завершился или ставка уже перебита, вернуть в соответствующее состояние, а не показывать false success.
5. После подтверждённого заказа объяснить, что площадка **не получила оплату**, что делать сторонам и где вернуться к сделке.
6. При ошибке сохранить безопасный контекст; контакты/персональные данные не сохраняются в публичном кеше.

## Спорный UX-вопрос: «Добавить товар, потом стать автором?»

Три альтернативы; это не просто перестановка двух кнопок.

| Вариант | Пользовательская польза | Стоимость и риски | Рекомендация |
| --- | --- | --- | --- |
| **A · Сократить заявку, сохранить gate** | Быстрое уменьшение шагов, нет новой модели прав | Ожидание автора остаётся | **Первое изменение для MVP**, если тест подтвердит трение |
| **B · Приватный Work draft до approval Seller** | Человек начинает создавать сразу, пока идёт проверка | ProductsService.create требует approved; новые права/медиа/recovery/quota/отклонения | **Прототипировать и оценить**, не встраивать без отдельного DEC |
| **C · Гостевой composer до регистрации** | Самый быстрый «вау» на старте | Временные файлы, перенос между аккаунтами, риски abuse/storage, потеря черновика | **Не делать сейчас** |

**Уточнение к варианту B:** при отклонённой заявке черновик остаётся строго private и не становится продаваемым; нужно определить хранение, лимиты, удаление медиа, выход из сессии, повторное обращение и отказ доступа. Публичный Work и Listing всё равно требуют всех approval.

## Другой спорный UX-вопрос: «Начинать с Work или сразу с Auction?»

**Для первой версии:** основной существующий вход **«Добавить работу»**, затем опциональная продажа из списка/страницы работы. Это самый безопасный вариант при готовой модели и модерации.

**На перспективу:** два входа намерения:
- «Показать работу» → Work wizard → public Work.
- «Продать / провести аукцион» → один guided wizard, который готовит Work, а позже и Listing, **после подтверждённых approval**.

Здесь нельзя создавать активный аукцион до Work approval или запускать таймер, который истечёт во время модерации. Нужно определить момент активации, черновик условий, необходимость повторного confirm и защиту от изменения цены. Дизайн гипотезу проверяем кликабельным макетом до backend-работ.

## 12 обязательных переходов для UX-ревью

1. Гость нажал «Добавить» → auth → правильное продолжение.
2. Гость нажал «Сохранить» → auth → та же Work.
3. Гость открыл bid sheet → auth → актуальная Work, **без автоставки**.
4. Новый автор вернулся после отказа/проверки → правильный статус.
5. Повторный отправленный запрос moderation → не отправляет дубликат.
6. Фото не загрузилось → другая фотография и текст не исчезли.
7. Закрыл приватный wizard → что сохранено, что требует повторного выбора.
8. Work approved → открытие публичной версии, а не старого preview.
9. Переход Work → Creator → Back восстанавливает контекст.
10. Listing закончился во время взаимодействия → цена/кнопка перечитаны.
11. Завершённый аукцион → результат и следующий шаг без ложной отметки об оплате.
12. Сделка закрылась или не состоялась → безопасный путь назад к Work/кабинету.

## Acceptance before implementation

Сперва сравнить реальные Figma состояния и работающий Web на 390/1024/1440, затем фиксировать изменения в соответствующем owner. В этом файле нет утверждения, что хотя бы одна из предложенных перестановок уже реализована.
